## Mapping constraints and explicit gaps

1. HTTP paths above are derived by combining frontend service literals and backend controller route/action attributes. No URI is represented as proof of a successful request.
2. The app's public `GET /api/categories` is a distinct-product-category projection from active `Products`; admin `/api/admin/categories` is CRUD over `Category`. These are related concepts, not the same endpoint or source.
3. The customer invoice JSON/PDF paths are nested under `/api/orders/{orderNumber}`. Admin invoice table listing is `/api/admin/invoices`; no standalone `/api/invoices` customer route was identified.
4. Refund operations have no dedicated controller/service HTTP route in the checked controllers. The source flow uses admin order status `RefundPending` then `Refunded`, with a `Refund` entity record. Provider-side refund processing is **NOT_MAPPED**.
5. UPI payment status is explicitly returned with `verified=false`; automated provider verification is **NOT_MAPPED** in the current source.
6. `OmDbContext` confirms the named `DbSet<T>` properties. Migrations confirm physical table names where created. This report does not claim that a live database has those migrations applied or that the deployment's schema matches them.
7. Frontend `ProtectedRoute` and route-key mapping are client-side declarations. API controllers independently authorize Admin, Customer, PartnerShop, or DeliveryPartner where source specifies it.
8. Route-level test mappings are **NOT_MAPPED** unless a specific test file is linked in the matching feature report. Tests that exercise helper/service behavior do not establish browser-to-database integration.
